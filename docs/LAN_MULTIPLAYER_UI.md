# 局域网联机 UI 设计研究

**范围**:只做 UI 设计研究,不写代码。架构、协议与已定决策见
`docs/LAN_MULTIPLAYER_DESIGN.md`,本文不重复,只引用。

**方法说明**:本项目的参考产品(围棋大师 1.4.0)**没有联机功能**——这不是印象,
是逐条查证的结果(§1.1)。因此这一份 UI **没有可抄的对象**,只能从已定决策反推。
凡是"约束推出来的"与"我建议的"是两回事,下文分别标注。

## 一、先确认:没有参考可抄

### 1.1 查证过程

对 `assets/flutter_assets/assets/localization/zh.strings`(1480 行,明文)做了穷举:

| 查什么 | 结果 |
| --- | --- |
| `"room` / `"lobby` / `"join` / `"host` / `"invite` / `"multiplayer` / `"online` / `"pair` / `"QR` / `"scan` / `"waiting for` | **各 0 条** |
| `"lan` | 1 条,是 **`Language`** |
| `"port` | 命中全是 **`Portuguese`**、`support` 一类 |
| 房间 / 大厅 / 联机 / 局域网 / 邀请 / 扫码 / 配对 | **各 0 条** |
| 玩家 | 3 条,全部关于**档案与 AI 对局里的玩家名** |
| 对手 | 2 条,是 **SRS 练习的"对手回应模式"** |
| `"6. Connection" = "6. 连接"` | 是**死活题主题**(连接/断),不是网络 |

**结论:参考产品的联网 UI 是一片空白**,连"房间""加入"这类词都没有出现过。
所以本项目的联机 UI 不能靠对齐竞品来降低风险,只能靠"把约束翻译成界面"。

这有一个副作用值得提前接受:**联机部分会是这个 App 里唯一没有既定风格参照的
功能**。它需要的控件(地址输入、口令、等待、断线横幅)在现有界面里都没有对应物,
视觉上必须自己立一套,而不是"照现有卡片风格拼一下"。

## 二、从已定决策直接推出的 UI 约束

这一节是全篇的地基。左列是 `LAN_MULTIPLAYER_DESIGN.md` 已拍的板,右列是它**强制**
产生的界面后果——不是设计选择,是推导结果。

| 已定决策 | 强制的 UI 后果 |
| --- | --- |
| 决定 3:Android 建房,Android 与 Web 都能加入 | 入口必须有**两个动作**:创建 / 加入。Web 端只能看到"加入" |
| 决定 4:同源 + HTTPS 两条路径并存 | 客户端**必须提供手输地址**;摄像头扫码只能是可选增强(同源路径是 http 页面,`getUserMedia` 不可用) |
| 决定 5:不做 mDNS,手动输入 | **地址是一等公民**:主机要把它显示得足够大、可复制;客户端要能粘贴 |
| 决定 6:不做前台服务,息屏即视为断线 | 断线是**正常状态而非错误**;UI 不能弹"连接失败"就结束,必须给出"等待重连 / 保留棋谱"的出口 |
| 决定 1:服务端权威校验 | 被拒的着手必须有反馈(否则玩家只看到自己点了一下没反应) |
| 决定 2:悔棋需对方同意 | 需要**双向**的悔棋 UI:请求方等待、被请求方决定 |
| 死子归属双方各自判断 | 需要**结果协商** UI:提交 → 对方确认 → 不一致时对比两份标记 |
| §5.4 房间令牌 | 客户端多一个输入项;主机多一块展示 |
| §3.3 实时用活会话、记录树管持久化 | 对局数据模型要能标出"这是联机对局",否则首页「继续」会把它显示成人机 |

**两条容易漏掉的推论**:

1. **规则在对局中不可改**。`设置` 面板能改棋盘路数/规则/贴目/让子,而联机双方
   各自持有一份会话——改了必然分叉。所以联机对局里**设置必须禁用**,不是"改完
   通知对方",而是根本不给入口。
2. **分析 = 作弊**。本项目的机器人面板在 AI 对局里提供「分析」(候选点+胜率)。
   联机时开着它下棋等于开狗。这跟社交礼仪无关,是**产品语义**问题:同一个按钮
   在对局中给引擎提示、在对局后给复盘,必须靠状态区分。

## 三、入口

### 3.1 位置

联机是"开一局新的",不是"管理已有棋谱",所以入口在**围棋首页的「快速开始」**,
不在棋谱库。

现有布局是两个等宽按钮:

```
快速开始
[ + 新建棋谱 ] [ 🤖 AI 对弈 ]
```

360dp 宽下每个约 156dp。加第三个按钮后每个只剩约 100dp,`新建棋谱` 四个字加图标
放不下,必然截断。所以改成两行:

```
快速开始
[ + 新建棋谱 ] [ 🤖 AI 对弈 ]
[ 📡 联机对弈                ]     ← 整宽
```

把联机单独放一行还有个好处:它确实是三种玩法里**唯一需要先做一件事才能开始**的
(建房或找房),给它更大的触区是合理的。

### 3.2 进去之后:先问"建还是加"

联机入口点进去是**一个只有两个选择的页面**(或底部弹层):

```
联机对弈
[ 创建房间 ]  把手机变成主机,把地址给对方
[ 加入房间 ]  输入对方屏幕上的地址
```

**Web 端只显示「加入房间」**——浏览器不能监听端口(设计文档 §2.1),给一个点了
必然失败的按钮比不给更糟。

**待定**:这一屏是独立页面还是底部弹层。倾向**弹层**:它只有两个选项,不承载状态,
不需要返回栈。

## 四、主机:房间页

这是整块 UI 里唯一"等待型"页面,信息密度最高。

### 4.1 布局

```
← 房间                                              [关闭]

        等待对手加入…

   ┌──────────────────────────────────┐
   │  192.168.1.23:8080        [复制] │   ← 大字,可点复制
   │  口令  4 2 7 1                    │
   └──────────────────────────────────┘
   (第一期到此为止;二维码见 §4.2b)

   玩家
   ● 房主(你)
   ○ 等待对手加入…

   规则   19 路 · 中国规则 · 贴目 7.5 · 分先
   执黑   你

   [            开始对局            ]   ← 对手未到时禁用
```

### 4.2 三个必须处理对的细节

**a) 地址可能不止一个。** `dart:io` 的 `NetworkInterface.list()` 在 Android 上会
同时给出 WiFi、热点、**VPN**、以及各种虚拟网卡。VPN 的地址(常见 `10.x.x.x`)对方
根本连不上。所以地址卡片必须是**可切换的下拉**:列出所有非回环 IPv4 接口,默认选
WiFi(tailscale/Clash 一类 VPN 接口要显式排除或至少排在最后)。

这一条不是锦上添花:**选错地址就是"对方连不上",而玩家无从判断是网络问题还是地址
问题**。界面上要能看到自己给出去的是哪个接口。

**b) 二维码:主机侧没有成本,但有依赖,建议放到第二期。**

设计文档 §2.3 说"扫码只作为 HTTPS 路径下的增强",这句话对,但**原因在客户端侧
不在主机侧**:主机只是画一张图,零成本零权限;能不能扫取决于客户端是不是安全上下文。

所以主机显示了也没用——**得先有客户端能扫**。而两边的扫码都有真实成本:

| 客户端 | 扫码要什么 | 成本 |
| --- | --- | --- |
| Android App | 条码扫描库 + **相机权限** | 新依赖 + 一个危险权限 + 权限被拒的分支 |
| Web(HTTPS 页面) | `getUserMedia` + JS 条码库 | 又要一个依赖,且只在 HTTPS 路径可用 |

**建议:第一期不做扫码**,只做手输 + 最近地址;主机屏幕上先不放二维码,放了也没人扫。
等手输链路跑通、确实觉得烦,再按上表选一条做。

**如果要做的两条注意点**:

- **二维码内容不要用自定义 scheme**(`easyplay://...`)。浏览器打不开这种链接,
  App 要处理它还得改 manifest 加 intent filter。更简单的做法是放**纯文本**
  `192.168.1.23:8080 4271`,由我们自己的扫描器解析——两边都不依赖系统去"打开"它
- 口令要放进码里,否则扫完还得再手输一遍,扫码就失去意义了

**c) 口令用 4 位数字。** 设计文档 §5.4 要求房间令牌(HMAC 校验),但**令牌的形式
是我们自己定的**。给玩家看一长串 hex 是不现实的(要靠手输),所以:握手时用 4 位
PIN,由主机在会话内校验。安全性上 4 位对"同一 WiFi 下的陌生人"够了——它不是防爆破,
是防"误连/顺手连";真要防爆破,主机侧对失败握手做速率限制即可(纯本地逻辑,不需要
改协议)。

### 4.3 开始对局

- **执黑/让子/规则由主机决定**,不设"猜先"。
  理由:服务端就是主机,任何"随机"都由主机产生且客户端**无法验证**。做一个看起来
  公平、实际不可验证的猜先,比不做更糟。要做的话只有两条路:承认"主机说了算",
  或者引入可验证随机(成本远超收益)。**建议不做猜先,由主机直接指定执黑。**
- 对手没进来之前,`开始对局` 禁用,并说明原因(而不是点了没反应)。
- 开局后**回到房间页**应该是可以的(比如同步失败要重新开局),但这是次要路径。

## 五、加入:三条路径,一个页面

客户端只有一种身份,但要覆盖三种实际情形。区分它们的是**页面所在的上下文**,
不是玩家的选择——所以 UI 应该自动适配,而不是让玩家选。

| 客户端情形 | 找主机的方式 | 说明 |
| --- | --- | --- |
| **Android App** | **主动扫描**(§5.0)+ 手输兜底 | 主路径 |
| **Web(主机同源 `http://192.168.1.23:8080`)** | **地址自动填好、只读** | 页面自己就是主机发的,地址即 origin |
| **Web(HTTPS 托管)** | 手输 | 浏览器**不能扫描局域网**(没有原始 socket),只能给地址 |

**Web 客户端是唯一真的"不能扫描"的一侧**——浏览器的沙箱里没有原始 socket,也没有
任何标准 API 能枚举局域网主机。Android 客户端没有这个限制。

(扫码不在第一期,理由见 §4.2b。)

Android 客户端的加入页因此长这样:

```
加入房间
  [ 扫描局域网 ]                       ← 主路径,点了才扫

  没找到?手动输入地址
  地址  [ 192.168.1.23 ]
  端口  [ 8080 ]
  口令  [ _ _ _ _ ]
  [ 加入 ]
```

扫描到多个房间时列成卡片(棋盘路数、房主、是否已满),点一张即填好地址与端口。

### 5.0 主动扫描:Android 客户端不该让人手输 IP

**先纠正一处措辞**:Android **完全可以**主动扫描局域网。本文档初稿只写了 mDNS 与
手输两条路,把"扫描"整个漏掉了——而设计文档决定 5 否决的是 **mDNS**,理由是组播在
真实网络里不可靠(AP 隔离、访客网络、多卡)。**主动 TCP 扫描不使用组播**,那条理由
对它不成立。

#### 怎么做

主机本来就要开一个 HTTP 服务(决定 4:给 Web 客户端发应用)。所以扫描不需要新端口:

```
客户端对本地 /24 的每个地址发一个 HTTP 请求
  GET http://192.168.1.x:8080/easyplay/probe

主机命中时回:
  200 {"app":"easyplay","version":1,"board":19,"players":1,"phase":"waiting"}
```

- **254 个地址,64 路并发,单个超时 250ms** → 最坏约 1 秒,正常半秒内出结果
- 用 `Socket.connect` + 一条极短的 HTTP 请求,`dart:io` 自带,不加依赖
- 探针路径是固定的,所以**误报几乎为零**(不像"8080 端口开着"就当成房间)
- 口令仍然要输:扫描只解决"找到主机",不解决"证明你能进"

#### 为什么这比手输好得多

| | 手输 | 扫描 |
| --- | --- | --- |
| 用户操作 | 找到、抄写、输入 12 位数字 | 点一下「扫描」 |
| 出错点 | 抄错、打错、主机换网卡后失效 | 无 |
| 需要新权限 | 无 | **当前无**(见下) |

#### 边界(必须同时保留手输)

| 情况 | 扫描 | 手输 |
| --- | --- | --- |
| 同一 WiFi、同一网段 | ✅ | ✅ |
| 路由器开了 **AP 隔离**(访客网络常见) | ❌ | ❌ 一样连不上 |
| 两台设备在不同网段(2.4G/5G 分了不同子网) | ❌ | ✅ 可能可以 |
| 客户端开了 VPN,流量被接管 | ❌ | ✅ 可能可以 |
| 公共 WiFi | 会对整个 /24 发 254 个连接,**别在别人的网络上这么干** | — |

所以:**扫描是默认路径,手输是兜底**。扫描失败时的文案要直接指向 AP 隔离这个最常见
原因,而不是只说"没找到"。

⚠ 最后一行是社交层面的注意点:扫描应该**只在用户点「扫描」时进行**,不能进页面就
自动跑;并且只扫本机所在的 /24,不做更宽的网段。

#### 真正的"不能":Android 17 的本地网络权限

设计文档 §2.4 已记:目标 API ≥ 37 的应用**默认禁止访问局域网**,必须申请
`ACCESS_LOCAL_NETWORK` 运行时权限。三个要点:

1. **Dart socket 弹不出权限框**。官方说明:socket 不与 Android UI 框架交互,没权限
   时 `Socket.connect` **直接抛 `SocketException`**。所以必须在建连**之前**,用
   `permission_handler`(`Permission.accessLocalNetwork`)申请完
2. 本项目 `targetSdk` 目前是 **36**,这条**尚未生效**;Flutter 升级会带到 37
3. **Android 16 上可以主动开启该行为提前测试**——应该在写联机功能之前先跑一次

UI 上的后果:扫描/加入之前可能要先弹一个系统权限框。所以「扫描」按钮的流程要设计成
**权限 → 扫描 → 结果**三段,而不是假设一定能扫。

**但那是 Android 17 的事**:Android 7 到 16 全段(设计文档 §2.5 有逐版本表)**只需要
`INTERNET`**,而项目已经声明了;不需要定位权限、不需要相机、不需要组播锁。所以第一期
的扫描与联机在 Android 7–16 上是"点一下就能用",不必先过权限这一关。

**同源 Web 那条是白送的好处**:页面从 `http://192.168.1.23:8080` 加载,它当然知道
主机是谁。所以那种情况下地址输入框应该**直接消失**,只留口令:

```
加入房间
  口令  [ _ _ _ _ ]
  [ 加入 ]
```

这同时也说明:**"打开主机的网址"本身就是加入流程的第一步**,Web 端不需要"输入
地址"这个概念。地址输入框只在 App 与 HTTPS 页面里出现。

### 5.1 输入体验

在手机上敲 IP 是最容易劝退的一步,所以要按最笨的办法优化。

**把地址拆成"IP + 端口"两个字段**,而不是一个 `192.168.1.23:8080`:

```
地址  [ 192 . 168 . 1 . 23 ]     自动补全
端口  [ 8080 ]                    通常不用动
```

这不是版式偏好,是键盘约束推出来的:

| 写法 | 键盘 | 结果 |
| --- | --- | --- |
| 一个字段 `ip:port` | `TextInputType.url` | 有 `/` 和 `.com`,**冒号要翻符号页**,容易卡住 |
| 一个字段 `ip:port` | `numberWithOptions(decimal: true)` | 有点,**但没有冒号**,根本打不出 `:` |
| **拆两个字段** | IP 用 `decimal` 数字键盘、端口用纯数字键盘 | 两边都只要数字和小数点,**完全不需要冒号** |

所以拆开之后两个字段都能用数字键盘,IP 里没有冒号、端口里也没有,这是唯一能
全程用数字键盘的排法。端口默认值填好,大多数人只需要输 IP。

其余几条:

- **粘贴要能拆**:从微信/QQ 复制过来的是 `192.168.1.23:8080`。粘进 IP 字段时,
  如果内容含冒号,**自动把后半段填进端口字段**。这是最常见的一次操作,不能让人
  手动分两半
- **最近地址列表**:连过一次就记住,点击即填。这是回访房间的主路径
- 校验放在提交时,并给出**具体**原因:`地址格式不对` / `连不上,检查是否同一 WiFi`
  / `口令不对` / `房间已满` / `版本不一致`

### 5.2 加入中的反馈

连接是异步的,失败原因有五种以上,不能只转圈。按状态给文案:

| 状态 | 文案 |
| --- | --- |
| 连接中 | 正在连接 192.168.1.23… |
| 地址不通 | 连不上这个地址。确认两台设备在同一个 WiFi,并检查主机屏幕上显示的地址 |
| 口令错 | 口令不对 |
| 房间已满 | 这个房间已经有两位玩家了 |
| 版本不一致 | 对方的主机版本与你不同,无法联机 |

**"连不上"的文案要带上主机地址**,因为最可能的原因是主机换了 IP 或选错了网卡
(§4.2a)。

## 六、对局中

### 6.1 工具栏怎么变

现有机器人面板是 `[AI 对弈] [分析]` → 展开 `设置 / 分析 / 停一手 / 悔棋 / 认输`。
联机时按 §二的两条推论收窄:

```
联机对局中的面板:
  停一手    悔棋    认输    联机信息
```

- `AI 对弈`:不出现(引擎绝不能接手)
- `分析`:不出现(§二.2,对局中给引擎提示 = 作弊)
- `设置`:不出现(§二.1,改规则必然分叉)
- 新增 `联机信息`:地址、对手、往返延迟、连接状态

**收窄的时机很关键**:这些按钮是"对局中"不可用,不是"永久不可用"。对局结束后
(终局/认输),`分析` 应该回来——复盘是联机的正当后续,而不是作弊。所以面板的
内容取决于 **`vsOnline && !gameOver`**,不是 `vsOnline`。

### 6.2 状态显示

现在的状态卡是:

```
黑方回合
提子：黑 0 · 白 0
```

联机时要补**对手侧的信息**,否则玩家无法区分"对方在想"和"对方掉线了":

```
黑方回合
提子：黑 0 · 白 0
● 对手在线 · 12ms
```

三种对手状态:

| 状态 | 触发 | 文案 |
| --- | --- | --- |
| 在线 | 心跳正常 | 对手在线 · 12ms |
| 长时间无动作 | 超过阈值(要宽松,设计文档决定 7) | 对手思考中… |
| 心跳超时 | 连续丢失 | 与对手失去联系,正在重连… |

**"对手思考中"和"失去联系"必须是两个不同的显示**,否则一手长考就会被误判成掉线
——而设计文档已经明确"超时判定要宽松"。宽到什么程度是参数问题,但 UI 上先分开。

### 6.3 悔棋

决定 2 要求请求—应答,所以有两个方向:

**请求方**(点了悔棋的人):

```
⚠ 已请求悔棋,等待对方同意…        [撤回]
```

**被请求方**:用 **MaterialBanner** 而不是 AlertDialog。

理由很具体:**同意悔棋之前需要看棋盘**。弹窗会盖住棋局,而"要不要让他悔"这个判断
依赖当前局面——尤其劫争附近。横幅停在顶部,棋盘始终可见。

```
⚠ 对方请求悔棋                        [拒绝] [同意]
```

**超时**:对方不响应时,请求方不能永远等;建议 30 秒后自动撤回并提示
`对方没有回应,悔棋请求已取消`。这个超时值属于产品参数,需要真实对局验证。

### 6.4 被拒绝的着手

服务端权威校验(决定 1)会让某些着手静默失败。玩家侧必须看得见:

```
SnackBar: 这一手不能下:该点已有棋子 / 自杀 / 劫争
```

**不能只是"点了没反应"**。而且这条路径**一定会被触发**——因为客户端本地的
`isLegalGoMove` 与服务端的判断可能因为版本/规则差异而不一致,这不是异常,是正常
路径。文案要给到具体原因,不是"操作失败"。

### 6.5 终局与计分

现有流程是:标记死子 → `确认计分` → 本地出结果。联机要改成两段式:

```
1. 双方各自标记死子(复用现有交互)
2. 一方点「提交结果」 → 全屏遮罩?不:横幅
   ⚠ 你已提交结果,等待对方确认…          [撤回]
3. 对方收到:⚠ 对方提交了结果                [查看] [确认]
4. 一致 → 终局写入;不一致 → 并排显示两份标记
```

不一致时不要"服务端裁决"(设计文档 §5.3 已排除全程权威)。给一个对比视图:

```
双方标记不一致
  你标出的死子    E15, F16
  对方标出的死子  E15
请协商后重新标记
```

**这是围棋本身的习惯**(双方确认),也是我们不做权威裁定的原因。

## 七、断线:UI 上是正常状态

决定 6 已经把断线接受为设计的一部分,所以 UI 的任务不是"避免断线",而是**让断线
可恢复、可理解、不丢棋谱**。

### 7.1 客户端失去主机

```
⚠ 与主机失去联系                    [重连] [保留棋谱并退出]
```

- `重连`:重新握手 + `stateRequest{lastSeq}` 补发缺失走子(设计文档 §3.2,天然幂等)
- `保留棋谱并退出`:把本地记录存下来,不再尝试。**这个出口必须有**——否则玩家会被
  困在一个永远连不上的页面上

### 7.2 主机侧

主机是权威,客户端掉线不影响它。主机看到的是:

```
○ 对手已离线,等待重连…
```

主机**不需要做任何事**,棋局和记录都在本地。对局可以继续等,也可以直接认输结束
(玩家自己的选择,不是程序判断)。

### 7.3 主机被杀 / 息屏后恢复

主机进程被杀**不丢棋谱**(走子已写进记录树,设计文档 §八)。所以恢复路径是:

```
重新打开 → 联机对弈 → 创建房间
  → 「上次的房间还在,继续这一局?」          [继续] [开新房]
```

这条路径的成本几乎为零,因为记录已经在本地了。但需要 UI 上明确提出这个选择,
否则玩家只会以为棋丢了。

## 八、屏幕常亮:一个便宜的补救

**这是本次研究里最有价值的一条。**

已定决策 6 放弃了前台服务,代价是"息屏即断连"。但 Doze 的触发条件包含**息屏**
(设计文档 §2.2 引用的官方文档),而 `FLAG_KEEP_SCREEN_ON` 恰好让这个条件不成立。

- **成本**:一个 MethodChannel 方法。项目已有 `easyplay/katago` 通道,加一个方法或
  新开一个通道都是一行 Kotlin
- **不涉及**:前台服务、服务类型声明、常驻通知、电池优化白名单、Play 审核
- **不改变决定 6**:仍然没有前台服务,仍然不做保活

**边界要说清楚,不能夸大**:

| 场景 | 屏幕常亮管用吗 |
| --- | --- |
| 无操作导致的自动息屏 | ✅ 管用,这是最常见的情形 |
| 玩家主动按电源键 | ❌ 不管用 |
| 切到后台/被其他 App 覆盖 | ❌ 不管用 |
| 系统内存回收 | ❌ 不管用 |

也就是说它把"息屏断连"从**必然发生**降为**需要玩家主动按电源键才会发生**。这不能
替代重连逻辑,但显著降低了它的触发频率。

**建议**:联机对局期间(仅主机侧,或双方都开)启用屏幕常亮,并在房间页明确告知
`对局期间屏幕会保持常亮`。这比"请勿息屏"的提示可靠。

⚠ 本条有一处**未实测**:`FLAG_KEEP_SCREEN_ON` 在 Flutter 的 `FlutterActivity` 上
是否能稳定跨页面生效。要像设计文档 §2.2 那样实测后再当真。

## 九、数据模型要动的地方

联机对局会被保存成普通棋谱,但现有的 `GoSavedRecord` 只有:

```dart
bool vsComputer;       // 是否对电脑
Side humanSide;        // 人类执哪边
GoAiSettings? aiSettings;
```

联机对局会落进 `vsComputer == false` 这一档,**和"新建棋谱(自己下)"完全无法区分**。
后果具体可见:

| 位置 | 现在会显示成 | 应该显示成 |
| --- | --- | --- |
| 围棋首页「继续」卡片 | `黑方 / 白方` | `我 / 对手`(或对手名) |
| 棋谱库列表 | `黑方 / 白方` | 同上 |
| 打开后的机器人面板 | `[新建棋谱]` 的形态 | 联机形态(§6.1) |

**所以要么加一个 `kind` 字段(`ai` / `record` / `online`),要么把 `vsComputer`
换成枚举。** 旧数据没有这个字段,读的时候要能降级(现有 `_decodeRecord` 已经在做
同类兼容,可以照办)。

这件事**必须在写联机功能之前定**,否则要么改一遍已有数据,要么 UI 上出现"联机对局
看起来像自己下的"。

另外:**联机棋谱两端各存一份,是两份独立记录,不同步**。这是"传走子不传状态"的
自然结果,不需要解决,但界面上不要暗示"双方共享棋谱"。

## 十二、分步实施建议

按"每步都能单独验证"排,且**先做不需要网络的部分**:

0. **先跑两个真机实验**(设计文档 §2.4 / §2.5),它们可能改变方案可行性:
   - **Android 16**:打开本地网络保护,跑一次"主机监听 + 客户端连接",确认是否
     需要权限、需要谁的
   - **Android 9**:release 包跑一次"扫描探针 + WebSocket + 主机 HttpServer",
     确认明文策略拦不拦 Dart 持有的 socket
   **这两步排在做任何联机实现之前。**
1. **数据模型**:给记录加 `kind`(§九),首页与棋谱库据此显示。**不碰网络**,可测试
2. **入口 + 房间页 + 加入页的纯 UI**:用假数据(写死的地址、假的心跳)把四个状态
   (等待/已加入/连接中/失败)都画出来。**不碰 socket**
3. **悔棋与计分的横幅**:先用本地假状态驱动,验证"同意前能看见棋盘"这件事成立
4. **屏幕常亮**:Kotlin 一行 + 实测跨页面是否生效(§八)
5. 然后才接 `ServerSocket`(设计文档第 3 步)

第 1–4 步都不需要网络,却把联机 UI 里最容易做错的部分(状态区分、出口、横幅 vs
弹窗)先定死了。第 0 步是**唯一必须先跑的真机实验**,因为它可能改变整个方案的可行性。
