## 一、开工前:两个阻断性实验

**这两件事排在所有实现之前。** 它们不是"验证一下",而是**可能改变方案可行性**——
尤其是第一条。

### 实验 A:Android 16 的本地网络保护(设计文档 §2.4)

要回答的问题:**主机监听是否也需要权限?**

官方措辞只覆盖 "discover, scan, or connect",**没有明说被连接的一方**。如果
`ServerSocket` 同样被拦,那不只是扫不到,而是**整个方案在 Android 17 上不成立**,
连"给浏览器发 Web 页面"都做不了。

步骤:

1. 在 Android 16 设备上开启该行为(开发者选项里可 opt-in 测试)
2. 跑一次最小验证:主机 `ServerSocket.bind` + 客户端 `Socket.connect` + 浏览器访问
   主机的 HTTP 服务
3. 分别记录:主机侧是否需要权限、客户端侧是否需要权限、报什么错

**记录格式**(写进 `LAN_MULTIPLAYER_DESIGN.md` §2.4):

| 角色 | 是否需要 ACCESS_LOCAL_NETWORK | 报错原文 |
| --- | --- | --- |
| 主机(监听) | ? | ? |
| 客户端(连接) | ? | ? |
| 浏览器(被发页面) | 不适用(浏览器有自己的策略) | ? |

**判定**:
- 只有客户端需要 → 按 `permission_handler` 方案做,`targetSdk` 升到 37 时补上
- 主机也需要 → 同样处理,但**必须在决定上线前解决**,否则新装机直接不可用
- 都不需要 → 说明 opt-in 行为与正式版不同,记录下来,`targetSdk` 升 37 时**重测**

### 实验 B:Android 9 的明文策略拦不拦 Dart 的 socket(设计文档 §2.5)

Flutter 那份 breaking-change 文档写着 "If the socket is owned by Dart/Flutter, no
policy will be enforced",但同一页又写着该变更 **Reverted in 2.2.0**,且官方声明不保证
更新。**所以不能按文档下结论。**

步骤:Android 9 真机 + **release 包**,分别验证

1. `Socket.connect` 到局域网地址(扫描探针)
2. `WebSocket.connect('ws://192.168.x.x:8080')`
3. 主机 `HttpServer` 被浏览器访问

**判定**:任一条被拦 → 需要 `networkSecurityConfig`。注意**Android 的 `<domain>` 不
支持网段**,没法只放行 `192.168.0.0/16`,只能全局 `cleartextTrafficPermitted="true"`。
这是要尽量避免的结果,也是为什么先测。

### 实验 C(可以并到实验 A 里做):手机热点当主机

没有路由器时的常见用法。热点网卡在 AOSP 上是 `192.168.43.1`,但 Android 11 起厂商
差异很大,有的对应用不可见(独立网络命名空间)。**逐机型测**
`NetworkInterface.list()` 能否列出热点网卡。

## 二、开发阶段

顺序经过设计:**D1 不碰网络,D2/D3 可并行,D8 最后**——因为禁用 AI 的判据要等
「这是联机对局」这个状态先存在。

### D1. 数据模型:`GoSavedRecord` 加 `kind`

**为什么第一步做这个**:现在只有 `vsComputer` 一个布尔,联机对局会和「新建棋谱」
完全无法区分,首页「继续」和棋谱库都会把它显示成「黑方/白方」。等联机功能写完再改,
就要动已有数据。

- 改成 `GoGameKind { ai, record, online }`,旧数据按 `vsComputer` 降级
- 首页卡片与棋谱库据此显示(`我 / 对手`)
- **联动检查**:`GoRecordSummary._playerNames` 现在按 `vsComputer` 分支,要一起改

**验证**:存储测试断言旧格式仍能读、三种 kind 各自的显示正确。
**退出标准**:`flutter test` 全绿,且新格式与旧格式的记录能同时出现在列表里。
**不碰网络。**

### D2. 主动扫描(纯 Dart 部分)

扫描可以完全脱离联机做:给它一个地址段,它返回哪些地址上跑着 EasyPlay 主机。

- 子网枚举:`NetworkInterface.list()` → 非回环 IPv4 → 各自的 /24
- 并发 TCP 连接 + 一条 HTTP 探针请求(`GET /easyplay/probe`)
- 超时与并发参数(254 地址 / 64 路 / 250ms)
- **扫到的结果要能区分"端口开着"和"是 EasyPlay 房间"**——探针响应里带 app 标识

**验证**:单元测试覆盖子网计算(边界:掩码不是 /24、多个网卡、VPN 接口);
真机上对着一台已知主机的假服务扫一次。
**退出标准**:扫一个 /24 在 1.5 秒内返回,漏扫与误报都为 0(对着已知的固定集合测)。
**依赖**:无。

### D3. 协议层 + 单进程双实例对打

**这一步是整个方案成立与否的证明**,而且完全不碰网络。

- 定义消息(`toWire` / `fromWire`),就是设计文档 §六 那张表
- 同一个进程里两个 `GameSession` 互相对打,断言:
  - 同一串走子重放得到同一局面
  - 非法走子被拒绝且**不改变状态**
  - 悔棋协商后双方一致(拒绝时也一致)
  - 乱序 / 重复 `seq` 被丢弃
  - 重连补发(`stateRequest{lastSeq}` → `stateSync`)后双方收敛
  - 计分协商:一致才写入终局;不一致时双方都不写

**验证**:就是上述断言本身,**全部进 CI**。
**退出标准**:这套测试是后续所有联机改动的安全网;它绿了才允许接真 socket。
**依赖**:无(可与 D2 并行)。

### D4. 联机 UI 骨架(假数据)

按 UI 文档把四类画面做出来,用写死的地址、假的心跳驱动:

- 入口(创建 / 加入)
- 房间页(地址、口令、玩家列表、规则摘要、开始按钮)
- 加入页(扫描、手输、最近地址、五种失败状态)
- 对局中的状态行与 MaterialBanner(悔棋请求、计分提交、断线)

**验证**:widget 测试逐状态断言;`连接中 / 连不上 / 口令错 / 房间已满 / 版本不一致`
五种文案都要能被触发到。
**退出标准**:不碰 socket 的情况下,所有状态都能在测试里出现。
**依赖**:无。

### D5. 屏幕常亮

- Kotlin 一行(`FLAG_KEEP_SCREEN_ON`),复用现有 `easyplay/katago` 通道或新开一个
- **必须实测跨页面是否生效**——这是 UI 文档 §八 标为未验证的一项

**退出标准**:真机上开房后屏幕不自动熄;离开房间后恢复系统行为。
**依赖**:无。可以和别的并行。

### D6. host / join 真链路

第一次真的连起来。范围要克制:

- 主机 `HttpServer` + WebSocket 端点 + 静态文件服务(Web 客户端)
- 客户端连接、握手、`hello` / `helloAck`
- 只做:连上、显示对手已加入、开始对局、走子互通

**不做**:悔棋、计分、重连、断线恢复(留给 D7)。
**验证**:两台真机,或一台真机 + 一台电脑浏览器。
**退出标准**:两台设备能下完一整盘棋(不悔棋、不断线),双方记录一致。
**依赖**:D3(协议)、D4(界面)、D2(扫描,可先用手输绕过)。

### D7. 语义补齐

- 服务端权威校验(`isLegalGoMove`)+ 被拒着手的反馈
- 悔棋请求/应答 + 超时
- 终局计分协商(**替换掉 `_autoAdjudicate` 的引擎裁定**)
- 断线重连 + `stateSync` 补发
- 主机恢复前台后的重建

**验证**:D3 的对打测试扩到这些流程;真机上手动制造断线(关 WiFi / 息屏)。
**退出标准**:任一方掉线重连后,双方局面与记录一致;计分必须双方同意才落盘。
**依赖**:D6。

### D8. 联机对局禁用一切 AI

按设计文档决定 8。**关键是做法**:不是逐个按钮去藏,而是**一个判据 + 一个守卫**。

- 一个 getter(如 `bool get _onlineGame => vsOnline && !session.gameOver;`)
- 每条 AI 路径入口加守卫:引擎启动、`genmove`、`kata-analyze`、`_autoAdjudicate`
- 界面据此隐藏:`AI 对弈`、`分析`、`选点`、`局势`、`AI 摘要`、`PV`、引擎设置项
- **特别检查 `_autoAdjudicate`**:它现在会在终局时调引擎判死子与算分,联机里必须
  整条换成 D7 的协商流程,而不是加个 `if` 跳过

**验证**:一条测试断言「联机对局期间任何路径都不会启动引擎」——用假引擎记录调用次数,
断言为 0。这比逐个断言按钮不存在可靠得多。
**退出标准**:对局结束后分析恢复可用(终局 → 复盘是正当的)。
**依赖**:D6/D7(需要"联机对局"这个状态真实存在)。

### D9. 真机矩阵联调

| 角色 | 设备 | 重点 |
| --- | --- | --- |
| 主机 | Android 7 与 16 各一台(若有) | 监听、发页面、息屏断线 |
| 客户端 A | Android | 扫描、加入、重连 |
| 客户端 B | 电脑浏览器(同源 http) | 地址自动填、无摄像头 |
| 客户端 C | 浏览器(HTTPS 页面) | LNA 权限提示、扫码(若做) |
| 异常 | 路由器开 AP 隔离 | 扫描与手输**都应失败**,文案要指对原因 |
| 异常 | 客户端挂 VPN | 扫描失败、手输可能可行 |
| 异常 | 主机开热点 | 热点网卡能否列出(实验 C) |

## 三、打包与部署

### 3.1 Android

**签名是上线的硬前提。** `build.gradle.kts` 已要求 release 构建读取
`android/key.properties`；缺失时失败，不再使用 debug 签名。密钥文件已忽略，发布者
仍需自行生成 keystore，并写入 `storeFile`、`storePassword`、`keyAlias`、
`keyPassword` 四项。**不要提交密钥。**
- 版本号:`pubspec.yaml` 的 `version: 1.0.0+1`,`+N` 是 versionCode,每次发布都要加

产物:

| 用途 | 命令 | 输出 |
| --- | --- | --- |
| 内测分发(直接装) | `flutter build apk --release --split-per-abi` | `app-arm64-v8a-release.apk` |
| 商店 | `flutter build appbundle --release` | `app-release.aab` |

**只需要 arm64-v8a**:KataGo 是 arm64 可执行文件,项目只有这一套 `.so`。

### 3.2 把 Web 构建打进 APK(同源路径的前提)

决定 4 的同源路径要求**主机把 Web 应用发给客户端**,所以 APK 里必须带一份
`build/web`。

**这是本次新增的打包依赖,也是体积的主要来源**:

| 内容 | 大小 |
| --- | --- |
| `build/web` 全量 | **55 MB** |
| 去掉 `*.symbols`(调试符号) | 47 MB |
| 再去掉 `skwasm*` / `wimp*` / `experimental_webparagraph`(不构建 `--wasm` 时用不到) | **31 MB** |

所以按 31 MB 计。裁剪清单:

```
build/web/canvaskit/**/*.symbols
build/web/canvaskit/skwasm*
build/web/canvaskit/wimp*
build/web/canvaskit/experimental_webparagraph/
```

**裁剪必须验证,不能想当然**:静态服务起 `build/web`,浏览器打开应用跑一局,在
Network 面板确认**没有 404**,尤其是 `canvaskit.wasm`(有两个:根目录一个、
`chromium/` 一个,按浏览器选择)。少一个就是白屏。

**打包时临时放进 `pubspec.yaml` 的 assets**:

```yaml
assets:
  - assets/web/            # 从 build/web 拷进来的裁剪结果
```

**这是本步骤最容易踩的坑**:`pubspec.yaml` 里写 `assets/web/` **只包含该目录下的
文件,不递归子目录**。而 Web 构建产物恰好是层层嵌套的:

```
assets/web/            顶层:index.html / main.dart.js / flutter.js ...
assets/web/canvaskit/          再加一层 chromium/、experimental_webparagraph/
assets/web/katago/
assets/web/assets/...          模型与本地化,同样有子目录
```

所以子目录要逐个登记,或者**由拷贝脚本生成这段清单**。项目里已有同样的做法可以照抄:
`assets/katago/THIRD-PARTY-LICENSES/` 既登记了目录本身,也逐个登记了其子目录里的
许可证文件——就是因为不递归。

**漏登记的症状是运行时 404**:主机发不出某个文件,客户端白屏或引擎起不来,而
`flutter build` 本身不会报错。

`tools/package_lan_android.py` 已实现此顺序：先 `flutter build web`，裁剪并复制到
`assets/web/`，临时将每个文件登记进 `pubspec.yaml`，再构建 APK；最后恢复
`pubspec.yaml` 并清理临时资源。调试验证运行
`python3 tools/package_lan_android.py --debug`，正式分发运行无 `--debug` 的命令。
商店 AAB 使用 `python3 tools/package_lan_android.py --appbundle`。
CI 已接入 debug 路径，避免 APK 内 Web 版本滞后。浏览器实际加载仍需真机验收。

### 3.3 Web 部署

按 `docs/DEVELOPMENT.md` §7,补充联机特有的两条:

1. **COOP/COEP 必须有**(`web/_headers` 已配)。缺了 → `SharedArrayBuffer` 不可用 →
   WASM 的 pthread 起不来 → 引擎不可用。**GitHub Pages 不能设置响应头,所以不能用来
   托管**;Netlify / Cloudflare Pages 这类支持 `_headers` 的可以
2. **HTTPS 路径会触发 Chrome 的 Local Network Access 提示**。这是浏览器策略正在收紧
   的方向(设计文档 §5.2),要有"某天突然连不上"的心理准备——同源路径就是为此准备的
   退路

发布后必须在**部署域名**上验证 `crossOriginIsolated === true`。

### 3.4 版本兼容约定

联机的两端必须有版本校验(协议里有 `hello {roomVersion}`)。约定:

- 主机与客户端的**棋盘/规则/贴目/让子**必须一致——不一致直接拒绝,不要试图兼容
- **APK 内置的 Web 构建产物必须与 APK 同一次构建**,否则同源客户端会用旧协议连新主机

- [ ] 两台 Android 能建房、加入、下完一整盘

- [ ] 手输地址在扫描失败的场景下可用
- [ ] 悔棋需要对方同意;拒绝后双方一致
- [ ] 计分需要双方确认;不一致时双方都不写终局
- [ ] 客户端断线重连后双方局面一致
- [ ] 主机息屏后客户端显示"失去联系",主机回来后能继续
- [ ] **联机对局期间引擎一次都没被启动**(用测试钉,不靠肉眼)
- [ ] 对局结束后分析恢复可用

### 权限与合规

- [ ] `AndroidManifest.xml` 只有 `INTERNET`(+ 视实验 A 结果决定是否加
      `ACCESS_LOCAL_NETWORK`)
- [ ] 若加了 `ACCESS_LOCAL_NETWORK`:隐私说明里写清**用途**("与本机同一 WiFi 下的
      设备互联对局"),否则商店审核会问
- [ ] 没有引入相机权限(扫码不在第一期)
- [ ] 没有引入定位权限(用 `NetworkInterface.list()` 枚举网卡而非 `WifiManager`)
- [ ] 开源许可页包含新依赖(`permission_handler` 等)

### 工程质量门

项目**目前没有 CI**(`.github/workflows` 不存在)。上线前至少要有:

- [ ] `dart analyze lib test` 干净
- [ ] `flutter test` 全过
- [ ] D3 的对打测试在 CI 里跑(**这是联机唯一能自动验证的部分,必须自动化**)
- [ ] release APK 能构建且**签名不是 debug**

### 回滚

## 五、不在本次范围

| 项 | 为什么 |
| --- | --- |
| 扫码加入 | 需要条码库 + 相机权限,且 Web 只在 HTTPS 路径可用(驱动决定:第二期) |
| mDNS / NSD | 组播在真实网络里不可靠(设计文档决定 5) |
| 前台服务 / 息屏保活 | 已明确放弃(决定 6),用屏幕常亮缓解 |
| 观战 | 协议天然支持(`seq` 广播),留口子 |
| 房间码(4 位数字代替 IP) | 没有中心服务器,短码解析不成 IP |
| 跨网段 / 互联网联机 | 需要服务器中转,是另一个项目 |
| 断线续弈的观战与回放 | — |

## 六、顺序与依赖

```
实验 A / B / C ──┐
                 │
D1 数据模型 ──────┤
D2 主动扫描 ──────┼──> D6 host/join ──> D7 语义 ──> D8 禁用 AI ──> D9 真机矩阵
D3 协议+对打 ─────┘                                    │
D4 UI 骨架 ───────────────────────────────────────────┘
D5 屏幕常亮 ──(独立,可随时插)
```

**关键路径是 D3 → D6 → D7**。D2/D4/D5 都可以并行或提前做,D1 必须先做(它是数据
格式)。

**工作量粗估**(改动面,不是工时):

| 步骤 | 面 | 主要成本在哪 |
| --- | --- | --- |
| D1 | 小 | 兼容旧数据 |
| D2 | 中 | 并发与超时参数调优 |
| D3 | 中 | 消息定义与边界断言 |
| D4 | 大 | 状态多、文案多 |
| D5 | 小 | 一次真机实测 |
| D6 | 大 | 第一次真连,坑都在这 |
| D7 | 大 | 悔棋/计分/重连三套协商 |
| D8 | 中 | 找全 AI 入口(尤其 `_autoAdjudicate`) |
| 打包 | 中 | Web 产物进 APK 的资产清单 |

## 七、风险

| 风险 | 什么时候暴露 | 应对 |
| --- | --- | --- |
| **Android 17 主机也被拦** | 实验 A | 若成立,**方案需要重做**(不能只做客户端权限);这是唯一可能推翻整个计划的项 |
| Android 9 明文策略拦 socket | 实验 B | 全局 `cleartextTrafficPermitted="true"`,接受安全姿态下降 |
| 热点网卡列不出来 | 实验 C | 热点场景退回手输 |
| **APK 体积 +31 MB** | 打包 | 裁剪清单;必要时第一期只支持 Android 客户端,同源 Web 延后 |
| Web 构建产物与 APK 版本不一致 | 发布流程 | 拷贝脚本 + 发布前强制检查 |
| 浏览器进一步收紧 Local Network Access | 持续 | 同源路径(决定 4)就是为此准备的退路 |
| 联机中漏掉一条 AI 路径 | D8 | 用"引擎调用次数为 0"的测试钉住,而不是查按钮 |
| 真机联调发现协议要改 | D9 | D3 的对打测试就是改协议的安全网 |
